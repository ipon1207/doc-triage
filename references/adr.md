# モード A — 決定を記録する（ADR）

決定記録は、更新しないから腐らない。半年後に方針が変わっても既存の記録は書き換えず、新しい記録を足して古いほうに「置き換え済み」と印をつけるだけ。この運用が崩れると普通の設計書に退化するので、書き換えたくなったときこそ新規追加を選ぶ。

## 進め方

### 1. 会話から拾えるものを拾う

決定の内容と背景は、たいてい直前の会話にある。すでに分かっていることを聞き直さない。

### 2. 足りないものだけ聞く

必ず埋まっている必要があるのは次の 3 つ。これらは枠がないと十中八九書かれないので、欠けていたら聞く。

- **何に困っていたか** — 決定の前にあった問題。これがないと、後から読んだ人に「なぜこんなものが必要だったのか」が伝わらない。
- **他に何を検討して、なぜ却下したか** — 書き手は採用した案の話しかしたくなくなるので、意識して聞く。半年後に誰かが同じ案を再提案したとき、この記述だけが議論の再燃を止められる。
- **この決定で何を諦めたか** — 一番効く項目。不利益が表面化したときに「想定内だったのか見落としだったのか」が分かる。

質問は一度に全部並べず、足りない順に 1〜2 問ずつ。相手が「特にない」と答えたら、それはそれで記録する価値がある情報として扱う。

ただし「諦めたものが何もない」と出た場合は、決定が自明すぎて記録の価値がない可能性が高い。その旨を伝えて、本当に書くか確認する。

### 3. 書く

ファイル名は通し番号＋短いタイトル。例: `docs/adr/0007-self-hosted-auth.md`

配置は、コードから物理的に近いほど寿命が延びる。同じリポジトリの `docs/adr/` を第一候補にして、社内 Wiki や共有ドライブは避けるよう勧める。

### 4. 再発見の仕掛けを 1 つ決める

書いただけの ADR は見つからない。必要になるのは半年後にそのコードを触る人で、その人は周知を聞いていないし、疑問を持つとも限らない。**疑問を持たずに変えてしまう人**を想定して設計する。

まず相手にこう聞く。**「この決定を知らずに変更されたら、何が起きますか」**

答えによって、必要な仕掛けが変わる。

| 答え | 仕掛け |
| --- | --- |
| 特に何も起きない / むしろ見直されるべき | 不要。ADR を書いて終わり |
| 実装がばらつく、意図が伝わらない | 対象コードにリンクコメントを 1 行入れる |
| 外部との約束が壊れる、数字がズレる、データ互換性が切れる | 決定を検証するテストを書く。加えて対象パスを CODEOWNERS に入れる |

コメントは理由を書くと腐るが、**ADR へのリンクだけなら腐らない**（決定は追記型で上書きされないため）。

```text
// 決済の端数は切り捨て。理由: docs/adr/0012-rounding-policy.md
```

テストで固定する場合は、テスト名か直上のコメントに ADR 番号を入れる。変更しようとした人はテストが落ちて止まり、そこから理由にたどり着ける。**文書は読まれないが、落ちたテストは必ず読まれる。**

ADR 側にも影響範囲（対象ファイルやディレクトリ）を 1 行書いておくと、コードから ADR、ADR からコードの両方向をたどれるようになる。

すべての ADR に仕掛けを付けない。上の表の 3 行目に当たるものだけでよく、大半は不要と判断されるのが正常。

### 5. 置き換えが起きたとき

古い記録は本文を書き換えない。状態を「置き換え済み（0012 による）」に変えるだけ。新しい記録の背景欄に、前の決定の何が問題だったかを書く。

## テンプレート

項目は 5 つまで。該当なしの項目は行ごと削ってよい（N/A を並べない）。

```markdown
# 0007. 認証に X を採用する

- 日付: 2026-03-14
- 状態: 採用

## 背景

（何に困っていたか。制約や期限があればそれも）

## 決定

（何をどうすることにしたか。1〜3 行）

## 検討した代替案

- Y — （却下した理由）
- Z — （却下した理由）

## 受け入れた不利益

（この決定で諦めたもの、将来問題になりうること）

## 知らずに変更されたら

（何が起きるか。「何も起きない」ならこの節ごと削る）
（影響範囲: 対象のファイルやディレクトリ。例: src/payment/Rounding.cs）
（仕掛け: 決定を固定しているテストなど。例: RoundingTests.端数は切り捨てられる）
```

状態は「採用 / 却下 / 置き換え済み（NNNN による）」のいずれか。却下した案も、検討した記録として 1 件書く価値がある場合がある。

## 書かないこと

- 実装の詳細。設定値、コード例、手順は ADR の仕事ではない。
- 現在の構成の説明。「今こうなっている」を書いた瞬間に腐る文書になる。
- 決定に至るまでの議論の全過程。結論と、却下した案と、その理由があれば足りる。

## 例

**入力**（会話から）

> 認証ライブラリ、結局 Auth0 やめて自前実装にした。予算が通らなかったのと、社内システムだから SSO 要件もなかったので

**確認すべきこと**

- 他に検討した選択肢はあったか（OSS ライブラリなど）
- 自前実装で何を諦めたか（保守コスト、脆弱性対応の責任など）
- この決定を知らずに変更されたら何が起きるか（この例では「自前実装をやめて外部サービスに戻す」判断はむしろ見直されてよいので、仕掛けは不要と判断できる）

**出力**

`docs/adr/0007-self-hosted-auth.md` を上のテンプレートに沿って 1 ファイル。背景に予算と SSO 要件の話、代替案に Auth0 と検討した OSS、不利益に脆弱性対応を自分たちで負う点を書く。「知らずに変更されたら」の節は削る。
