# モード B — 既存の文書を診断する

渡された文書の中から「更新され続けないと嘘になる箇所」を拾い、腐らない形への変換案を出す。

目的は文書を減らすことではなく、**維持コストを払う対象を選び直すこと**。全部消せという結論にはまずならない。

## 進め方

### 1. 文書を読み、現在形の主張を拾う

「〜である」「〜を使っている」「〜という構成になっている」と現在の状態を断言している箇所が候補。過去形の記録（決定、議事録、調査メモ）は最初から対象外なので飛ばす。

### 2. 拾った箇所を分類する

| 分類 | 見分け方 | 変換先 |
| --- | --- | --- |
| 自動生成に寄せる | コードやスキーマから機械的に導出できる（API 仕様、依存一覧、テーブル定義、フォルダ構成） | 生成物へのリンク、または生成の仕組み |
| 単一の情報源へリンクする | どこかに実物がある一覧を転記している（環境 URL、権限一覧、担当表） | 実物へのリンクだけにする |
| 過去形にできる | 「なぜそうしたか」が現在形で書かれている（技術選定、方針、設計意図） | ADR として切り出す |
| 実行可能にする | 手順書（環境構築、デプロイ、障害対応、バックアップ） | スクリプトや Makefile にする。文章のままだと壊れても誰も気づかない |
| 役目を終えている | 書く過程で設計を詰めること自体が目的だったもの（詳細設計書、検討メモ、移行計画） | 触らない。腐っているのが正常な状態であって、直す対象ではない |
| 残す（確認日を付ける） | 上のどれにもならず、それでも必要なもの | 分量を絞り、最終確認日を明記する |

「役目を終えている」を独立させているのは、**指摘としては正しいが直させると無駄になる**文書があるため。詳細設計書が実装と乖離していることを指摘するのは簡単だが、その文書はすでに価値を回収し終えている。乖離の指摘と、直すべきという指摘を混ぜない。

### 3. 害の大きい順に並べる

腐っている度合いだけで並べない。誰も開いていない文書は、腐っていても実害が発生しない。優先順位は**腐敗度 × 実際に読まれる頻度**で決まる。読まれているかどうかは、Wiki の閲覧数、新しく入った人がどこで質問してきたか、レビューで参照されたかから分かる。分からなければ聞く。

指摘は多くても 5 件まで。優先順位はこの順。

1. **外部が信じて動くもの** — API 仕様、インターフェース定義。ズレると他チームや他システムを巻き込む。
2. **緊急時に開くもの** — 障害対応手順、連絡先、エスカレーションフロー。古かったら致命的。
3. **新しく入った人が最初に読むもの** — 環境構築手順、オンボーディング。間違っていると最も弱い立場の人が詰まる。
4. **それ以外**

全部直せと言わない。一度に直せるのは 2〜3 件で、それ以外は「今は触らない」と明言したほうが実行される。

### 4. 更新トリガーを提案する

残すと決めた文書には、更新されるきっかけを既存の作業フローに埋め込む案を 1 つ添える。

- PR テンプレートに項目を足す（「構成図の更新が必要か」）
- リリースチェックリストに入れる
- 手順を実行して詰まった人がその場で直すルールにする
- 最終確認日を書いておく（これだけでも読む人が疑えるようになる）

トリガーを設計できない文書は、腐る前提で分量を最小化する。

## 出力の形

診断結果は表で返す。文書全体を書き直して返すのではなく、どこをどうするかを示す。

```markdown
## 診断結果

| 箇所 | 分類 | 提案 |
| --- | --- | --- |
| 「API エンドポイント一覧」 | 自動生成に寄せる | OpenAPI スキーマを正にして、この節はリンクに置き換える |
| 「技術選定の背景」 | 過去形にできる | ADR 0001 として切り出す。以降は追記のみ |
| 「環境構築手順」 | 実行可能にする | セットアップスクリプト化。当面は最終確認日を記載 |

## 今回触るべきは上の 3 件

残りは分量が少なく実害も小さいので、今は触らない。
```

その後、相手が希望すれば実際の変換（ADR の切り出し、スクリプト化、書き直し）に進む。診断だけで終わってもよい。

## 注意

- 文書の著者を否定しない。腐るのは書き方の問題ではなく、その種類の文書が構造的に腐るだけ。
- 図が細かすぎるのは典型的な症状。矢印を 10 本描いた図は 1 本変わるたびに嘘になり、3 本の図はめったに嘘にならない。情報量を減らすほど寿命が延びると伝える。
- 計画・進捗・課題一覧が Wiki にあったら、それは文書ではなくチケット管理ツールの領域。文書として直すのではなく、置き場所ごと移すことを勧める。
