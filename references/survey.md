# モード D — リポジトリを調べて方針を出す

まだ文書がほとんどない、あるいは何から書けばいいか分からない状態から始めるときのモード。リポジトリの現状を把握し、「何を書き、何を書かないか」を順序付きで示す。

このモードの成果物は文書そのものではなく**方針**。いきなり文書を量産しない。網羅的な計画は必ず実行されずに終わるので、最初に書くものを 3 件に絞ることを目的にする。

## 構造的な限界を先に理解する

リポジトリから読めるのは「今どうなっているか」だけ。**「なぜそうしたか」はコードのどこにも存在しない。**

だから調査結果から ADR を書き起こしてはいけない。背景や却下理由を推測で埋めた記録は、本物の記録より有害になる（読んだ人が事実として信じるため）。決定らしきものを見つけたら、候補として挙げて人に聞く。これが唯一の正しい扱い方。

## 進め方

### 1. 読める環境か確認する

リポジトリにアクセスできない場合は、聞き取りで代替する。その場合は次の 4 つを聞けば足りる。

- 何をするシステムで、誰が使うか
- 外部と何を連携しているか
- デプロイされる単位はいくつあるか
- 新しく入った人が最初に詰まるのはどこか

### 2. 浅く、広く見る

全部読まない。次の順で、構造が分かるところまでで止める。

| 見るもの | 分かること |
| --- | --- |
| README、`docs/`、Wiki へのリンク | 既存文書の有無と鮮度 |
| パッケージ定義（`package.json`、`go.mod`、`pyproject.toml` など） | 技術構成、外部サービス依存 |
| Dockerfile、compose、CI 設定、デプロイ設定 | レベル 2 の実行単位 |
| 環境変数の定義、SDK の依存 | レベル 1 の外部境界 |
| 最上位 2 階層のディレクトリ構成 | レベル 3 の層構造があるか |
| テストの置き場と量 | 振る舞いがコードで語られているか |

コミット履歴や個別の実装には踏み込まない。深追いすると調査自体が目的化する。

### 3. 3 種類に仕分ける

**(a) 事実として書けるもの — レベル 1・2**

コードから読み取れるので、下書きを出してよい。ただし提示して確認を取る。

**(b) 仮説としてしか書けないもの — レベル 3**

既存コードから読み取れるのは「観測された慣習」であって「意図されたルール」ではない。「こういう慣習があるように見えるが、これは意図したルールか、たまたまか」と必ず聞く。たまたまなら書かない。

**(c) 人に聞かないと書けないもの — 決定の背景**

技術選定、アーキテクチャの選択、避けている手法。候補を挙げて聞く。書くと決まったらモード A へ渡す。

### 4. 順序を決める

**不在の害が大きい順**に並べる。判断基準は「新しい人が入ってきて、どこで詰まるか」。

典型的な順序は次のようになるが、リポジトリの状態で変わる。

1. 環境構築手順（動かせないと何も始まらない）
2. レベル 2 の構成図（全体像がないと調査に時間がかかる）
3. レベル 1 の境界（外部連携が多い場合は順位が上がる）
4. ADR を積み始める（今まさに決定が発生している時期なら順位が上がる）
5. レベル 3 のルール（人が増えて実装がばらつき始めてから）

既存文書があるなら、先にモード B で診断する。腐った文書が残っている状態で新しい文書を足すと、どちらを信じるべきか分からなくなる。

## 出力の形

```markdown
## 現状

（3〜5 行。何があって、何がないか）

## 書かないもの

| 対象 | 理由 |
| --- | --- |
| API エンドポイント一覧 | 型定義から読める |
| ディレクトリ構成の説明 | コードを見れば分かる |

## 最初に書く 3 件

1. **環境構築手順** — 現状セットアップが README に 2 行しかなく、初回で詰まる。スクリプト化を推奨
2. **レベル 2 の構成図** — API とバッチとフロントの関係が読み取りにくい。箱 5 個の図 1 枚
3. **ADR を積み始める** — 直近で決めたことが 3 件ほどありそう（下記）。まずそこから

## 確認したいこと

- (c) で拾った決定の候補。それぞれ「これは記録する価値があるか」を聞く

## 今はやらないこと

（レベル 3 のルール整備など、時期尚早なものを明示する）
```

最後の「今はやらないこと」を必ず書く。これがないと、提案が「いつかやるべきことリスト」として溜まり、結局どれも実行されない。

### モード B と併用するとき

既存文書があってモード B の診断を先に出した場合、モード D の節では診断表で述べたことを繰り返さない。「書かないもの」の表は、**文書として存在しないもの**だけを扱う。既存文書に「書かない」と診断したなら、それは診断表の側の話。

行動リストも 1 本にまとめる。モード B の「今回触るべき」とモード D の「最初に書く 3 件」を別々に置かない。既存文書の修正と新規に書くものを混ぜて、合計 3 件までの 1 リストにする。

## やらないこと

- 網羅的な文書計画を出す。10 件のリストは 0 件と同じ。
- テンプレート一式を先に配る。実際に数件書いてから、毎回同じことを考えていると分かった時点で作る。
- 調査結果から ADR を書き起こす。背景は人に聞く。
- 記述と実態のズレを成果物にする。既存文書があるなら診断はモード B の仕事で、そこでも内容の正誤は扱わない。
- ディレクトリやファイルを勝手に作成する。方針に合意が取れてから。
